# JoPilot

**Evidence-driven personal intelligence built around real life, trustworthy state, and human judgment.**

JoPilot is an experimental personal intelligence system built around a simple thesis:

> **JoPilot observes the normal evidence generated by someone's life and work, maintains state across it, and surfaces the right context when that context becomes useful.**

Most personal productivity systems ask the person to maintain the system. JoPilot explores the opposite approach: let normal behavior generate evidence, preserve what that evidence actually supports, reconcile it into trustworthy state, and ask for human judgment only when judgment is genuinely needed.

## What problem is JoPilot exploring?

Small responsibilities often take only minutes to complete but carry much larger cognitive activation costs: notice the signal, reconstruct context, investigate, decide, act, and remember to return if interrupted.

JoPilot's goal is to carry that surrounding burden.

> **JoPilot should carry the problem until it reaches the smallest irreducible piece that requires me.**

## Product loop

```text
Normal life
    ↓
Evidence
    ↓
Trustworthy state
    ↓
Context + insights
    ↓
Human judgment where needed
    ↓
Bounded, reversible action
    ↓
Reality provides new evidence
```

The goal is not autonomous action for its own sake. The goal is to move cognitive and administrative burden from the person to the system **without moving judgment and control away from the person**.

## Architecture

JoPilot is evolving around five conceptual layers:

1. **Evidence** — preserve what actually happened, where it came from, and when it became available.
2. **State** — maintain durable people, relationships, commitments, tasks, decisions, and open loops.
3. **Reconciliation & intelligence** — connect evidence to state while preserving uncertainty and provenance.
4. **Judgment** — surface the small number of decisions that genuinely require a human.
5. **Action** — perform narrowly scoped, reversible actions only when the evidence and authorization support them.

See [ARCHITECTURE.md](ARCHITECTURE.md).

## Engineering principles

- **The architecture should become more sophisticated so the interface can become less sophisticated.**
- Evidence and interpretation are different things.
- Corrections should append to history, not rewrite it.
- **Correct what the evidence proves. Preserve what you don't know.**
- Relationship edges need type, direction, and provenance.
- Authorization should be proportional to consequence.
- Uncertain write outcomes should be reconciled by readback, not blind retry.
- A green test suite is not the same thing as production truth.

See [PRINCIPLES.md](PRINCIPLES.md).

## Patient 0

JoPilot is being developed as a **Patient 0** project: real workflows generate the requirements and real use tests whether the system's assumptions survive contact with reality.

Two examples:

- **Reality outranks fixtures.** Early natural production evidence exposed a decoder defect the offline suite had missed. The original bad capture was preserved, the decoder was repaired structurally, and later natural evidence validated the repaired path.
- **Useful graphs must preserve uncertainty.** A relationship insight once compressed an unresolved intermediary into an apparent direct connection. Testing the insight in the real world falsified that stronger claim.

See [CASE-STUDIES.md](CASE-STUDIES.md).

## Current public status

This repository is a **sanitized product and architecture showcase**, not the production JoPilot source repository.

The private Patient 0 system currently has:

- verified live evidence capture against naturally arriving data;
- forward-only candidate extraction deployed behind a separate activation boundary;
- correction-aware evidence interpretation;
- provenance-bound attribution and review machinery;
- guarded, idempotent write/recovery patterns; and
- hundreds of offline regression tests plus a separate federation acceptance suite.

Downstream operational actions are being activated incrementally rather than all at once.

See [MILESTONES.md](MILESTONES.md).

## AI-native building

This project is also an experiment in how software gets built in the age of AI.

I am not presenting myself as a career software engineer who hand-authored every line. I am exploring what becomes possible when a product and technology leader combines problem discovery, systems thinking, product judgment, architecture, AI coding agents, automated tests, production canaries, and real-world feedback into a tight build-measure-learn loop.

The interesting question is not whether AI can generate code. It is whether a person can use AI to build **trustworthy systems that survive contact with reality**.
